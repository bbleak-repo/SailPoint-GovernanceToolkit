1. API: duplicate /v3 version segment — ~10 exported functions always 404

CRITICAL   Commit dbb6066   Files: Modules\SP.Api\SP.ApiClient.psm1, Modules\SP.Core\SP.Config.psm1

Impact before the fix: Api.BaseUrl is configured with the version segment (https://tenant.api.identitynow.com/v3) and the client concatenated endpoints verbatim — but 14 call sites passed endpoints that also began with /v3/. The resulting /v3/v3/… URLs 404 on every tenant, which silently killed: Get-SPEntitlementInventory, Get-SPAccessProfileInventory, Get-SPRoleInventory, Save-SPConfigurationSnapshot, Get-SPOrphanAccounts (worst case: the per-source 404 caused a break, returning an empty result as success), Get-SPSourceAggregationHealth, Measure-SPIdentityDataQuality, and Test-SPSourceOnboardingReadiness.
Before — SP.ApiClient.psm1
$baseUrl       = $config.Api.BaseUrl.TrimEnd('/')
$cleanEndpoint = if ($Endpoint.StartsWith('/')) { $Endpoint } else { '/' + $Endpoint }
$fullUrl       = $baseUrl + $cleanEndpoint + $queryString
# '/v3/entitlements' + BaseUrl '.../v3'  =>  https://tenant.../v3/v3/entitlements  (404)
After
# Version-segment normalization: if the base URL's last path segment (v3, v2,
# beta, ...) matches the endpoint's first segment, drop the duplicate so BOTH
# endpoint styles ('/campaigns' and '/v3/campaigns') resolve correctly.
$baseVersionSeg = ($baseUrl -split '/')[-1]
if ($baseVersionSeg -match '^(v\d+|beta)$' -and
    ($cleanEndpoint -eq "/$baseVersionSeg" -or
     $cleanEndpoint.StartsWith("/$baseVersionSeg/", [System.StringComparison]::OrdinalIgnoreCase))) {
    $cleanEndpoint = $cleanEndpoint.Substring($baseVersionSeg.Length + 1)
    if (-not $cleanEndpoint.StartsWith('/')) { $cleanEndpoint = '/' + $cleanEndpoint }
}

The central fix was chosen over editing all 14 call sites so existing external callers of either style keep working, and future call sites cannot reintroduce the bug. No caller in the repo uses /beta endpoints, so the normalization changes no other behavior. VERIFIED: 6-case matrix incl. case-insensitive /V3/ and version-less BaseUrl

Test-SPConfiguration connectivity / entity validation repaired in the same commit

The -ValidateConnectivity / -ResolveEntities paths could never succeed, for four stacked reasons:

  • Called Get-SPAuthToken -Config $config and Invoke-SPApiRequest … -Config $config — neither function has a -Config parameter, so every call threw a ParameterBindingException that was reported as a config error.
  • if ($token) was truthy even for the @{Success=$false} failure envelope — a failed auth would have reported "authentication successful".
  • Read $source.name / $identity.name off the response envelope instead of .Data, so every real entity resolved to "not found in tenant".
  • Used /v3/… endpoints (the duplicate-segment bug) and GET /identities/{id}, which does not exist in the ISC v3 API — now uses /search/identities/{id}, matching SP.IdentityService.

5. Cache: -RefreshCache never refreshed; the meta sidecar could lie about provenance

HIGH   Commit 29d9982   File: Modules\SP.Audit\SP.AuditQueries.psm1 (Get-SPCachedCampaignItems)

Impact before the fix (four related defects in the campaign items cache):
  • -RefreshCache was a no-op on reads. Both cache-read layers gated only on -not $NoCache, so -RefreshCache alone returned the existing hit. Because COMPLETED campaigns are cached as permanent, a completed campaign's cache could never be refreshed with this flag — despite the code's own contract: "-RefreshCache: skip read but DO write".
  • The -NoCache -RefreshCache workaround corrupted provenance. It streamed fresh items to disk but the finalize block started with if ($NoCache), so the meta sidecar was never rewritten. Fresh items then sat next to the old meta; if that meta said Status=ACTIVE and the campaign had completed, the seal-on-transition path stamped freshly fetched post-completion data as CapturedWhileActive=$true / Unverified=$false — the flags the reporting layer uses to distinguish honest ACTIVE-state data from ISC's post-completion rewriting.
  • The partial-fetch resume path ignored both switches, so a leftover partial file was silently blended into a "fresh" -NoCache/-RefreshCache pull.
  • Pure -NoCache fetches polluted the session memory cache. The fresh bypass pull (marked permanent for COMPLETED campaigns) was stored in memory, so the next default call served it instead of the preserved honest disk cache — contradicting "fresh data is only used for this run".
Before
if (-not $NoCache -and $script:_ItemMemCache.ContainsKey($campId)) { ... return cached }   # layer 1
if (-not $NoCache -and $isCacheable -and (Test-Path $itemsFile) -and (Test-Path $metaFile)) { ... }  # layer 2
if ($isCacheable -and (Test-Path $itemsFile) -and -not (Test-Path $metaFile)) { resume partial }
...
if ($NoCache) { "RefreshCache mode" message -- but meta2 never written }
elseif ($writeToCache -and $allItems.Count -gt 0) { meta2 write }
...
$script:_ItemMemCache[$campId] = $memEntry3   # unconditional
After
if (-not $NoCache -and -not $RefreshCache -and $script:_ItemMemCache.ContainsKey($campId)) { ... }
if (-not $NoCache -and -not $RefreshCache -and $isCacheable -and ...) { ... }
if (-not $NoCache -and -not $RefreshCache -and
    $isCacheable -and (Test-Path $itemsFile) -and -not (Test-Path $metaFile)) { resume }
...
if ($NoCache -and -not $RefreshCache) { pure NoCache: preserve disk cache }
elseif ($writeToCache -and $allItems.Count -gt 0) { meta2 write -- now also runs for
    -RefreshCache and -NoCache -RefreshCache, keeping items + meta consistent }
...
if (-not ($NoCache -and -not $RefreshCache)) {           # pure -NoCache skips memory too
    $script:_ItemMemCache[$campId] = $memEntry3
}

Semantics now match the documented contract exactly: default = read-through with TTL; -RefreshCache = skip reads, full re-pull, rewrite items+meta; -NoCache = fully fresh data for this run only, disk and memory caches untouched. VERIFIED: AST parse clean; decision table walked for all four switch combinations

6. Auth: dead tenant-isolation guard; JWT decoded as base64url

HIGH   Commit d253c8d   File: Modules\SP.Core\SP.Auth.psm1

Impact before the fix: the "TENANT ISOLATION GUARD" in Get-SPAuthToken — which exists to prevent a token acquired for tenant A being served to a toolkit instance re-configured for tenant B in the same powershell.exe process — read $config before the $config = Get-SPConfig assignment (which sits after the cache checks). The configured tenant URL was therefore always empty: the mismatch eviction could never fire, and TenantUrl was never stored alongside cached tokens, so the guard was dead code on every path. Independently, Set-SPBrowserToken decoded the JWT payload with standard Base64 — JWT segments are base64url-encoded, so extraction threw (silently) for any payload containing -/_, i.e. most real ISC tokens, and browser tokens never carried a TenantUrl either.
Before

    try {
        $configTenantUrl = ''
        if ($null -ne $config -and ...)          # $config = Get-SPConfig happens ~55 lines LATER
            $configTenantUrl = [string]$config.Authentication.ConfigFile.TenantUrl
...
$payloadB64 = $segments[1].PadRight(($segments[1].Length + 3) -band -bnot 3, '=')
[System.Convert]::FromBase64String($payloadB64)   # throws on '-' or '_'
After
if (-not $Force) {
    try {
        $configTenantUrl = ''
        $guardConfig = $null

        if ($null -ne $guardConfig -and ...) { $configTenantUrl = [string]$guardConfig...TenantUrl }
...
$config = Get-SPConfig
# (Re)compute for the cache-store step, so TenantUrl is stored on ALL
# acquisition paths -- including -Force.
$configTenantUrl = '' ; if (...) { $configTenantUrl = [string]$config...TenantUrl }
...
# JWT segments are base64URL-encoded: map the URL-safe alphabet first.
$payloadB64 = $segments[1].Replace('-', '+').Replace('_', '/')
$payloadB64 = $payloadB64.PadRight((($payloadB64.Length + 3) -band -bnot 3), '=')

VERIFIED: base64url decode reproduced — old code throws on a real-shaped payload, new code extracts the issuer URL

7b. Single-operation JSON Patch serialized as an object (HIGH)

The pipeline unrolls a single-element array, so a one-op RFC 6902 patch — the most common case — was sent as {...} instead of [{...}] and rejected by ISC with 400.

$invokeParams['Body'] = $Body | ConvertTo-Json -Depth 20       # 1-op patch: '{...}'
$invokeParams['Body'] = ConvertTo-Json -InputObject $Body -Depth 20   # 1-op patch: '[{...}]'

VERIFIED: before/after serialization compared in PS 5.1

7c. Transient API failures poisoned the identity cache for the whole session (HIGH)

The SPIdentity / SPEmailLookup stores never expire in-memory (TTL 0). A single 429/timeout cached Found=$false, so that identity rendered as a blank name/manager in every report for the rest of the session. Failure results now carry a 15-minute per-item TTL (a capability SP.CacheService already supported); successful resolutions keep their original session + disk caching, and genuine zero-hit searches still cache for the session.

Set-SPCachedItem -Store 'SPIdentity' -Key $IdentityId -Value $emptyResult -NoPersist -TtlMinutes 15

VERIFIED: failure entry expires and refetches after TTL; success entry survives (timestamp-rewind test)

7d. Identity disk-cache compaction silently no-oped when everything expired (MEDIUM)

Write-SPHtmlFile declared [Parameter(Mandatory)][string]$Content; PowerShell rejects an empty string for a mandatory string parameter, and Import-SPIdentityCacheFromDisk swallowed the exception — so whenever all cached identities had expired (e.g. the first run of a new day past the 24h TTL), the stale file was never compacted or emptied.

[Parameter(Mandatory)]
[AllowEmptyString()]
[string]$Content

9. Round 3 — reassignment-stable scope key + four user-decided semantics changes

The scope-key change was driven by a user-reported requirement; the four semantics changes (D4/D5/E4/C3) were decided interactively — each option was presented with its headline-KPI consequences and the recommended choice was approved.

9a. Reassignment-stable scope key (finding F1) — 758f707 HIGH

The requirement: campaigns and "newly approved" items must be linked to the real cache and the user's primary key — an entitlement reassigned to a new reviewer must NOT report as newly approved. The defect: every scope key in the toolkit (snapshot Key, diff maps, series ItemKey, V3's Get-V3Key, entitlement-history timelines) was AccessId-first — but ISC regenerates access ids when a certification is reassigned (already detected by Invoke-SPCacheDiagnostic's cross-campaign check, which called out exactly this false-"newly added" mechanism). A reassigned grant changed keys between captures: the diff engine classified it Removed+Added ("newly in scope"), the series engine NewlyInScope/NewlyAttested, and a decision on it reported as "newly approved".
Before
Key = IdentityId | AccessId (regenerated on reassignment) | SourceId
→ reassignment: old key vanishes (Removed), new key appears (Added/"newly approved")
After
Key = IdentityId | AccessName (lowercased; AccessId only when name blank) | SourceId-else-name
→ reassignment: key unchanged; decisions carry over
# shared Get-SPStableScopeKey (SP.CampaignDelta, exported); the diff maps, entitlement-history
# timelines, scope CSV, and V3 RECOMPUTE the key from persisted fields at load time, so old
# (AccessId-keyed) snapshots stay comparable with new ones -- no avalanche diff on upgrade.

Accepted trade-off (user-approved): an entitlement RENAME churns once as removed+added; same-named entitlements on one source for one identity collapse to one key. VERIFIED: simulated reassignment (new cert id + regenerated AccessId, same grant) through Build-SPCampaignSnapshotData + Compare-SPCampaignSnapshots yields Added=0 / Removed=0 (was 1/1); CD-06 rewritten as a reassignment-stability regression test; 121/121 delta/diff/series/trend/V3 tests pass

9b. D4 — honest pending decision dates + decided-only rubber-stamp metrics — 444be5f

Pending items no longer get the modified/created fallback as a fabricated DecisionDate (undecided rows render blank instead of "decided at campaign creation"). Rubber-stamp metrics analyze decided items only: the approval-rate denominator now matches its own documentation ("% of decisions that are APPROVE") — reviewers previously masked by pending items in their denominator will now correctly flag — and shared fallback timestamps can no longer fabricate bulk-decision clusters.

9c. D5 — distinct-reviewer executive KPIs — 444be5f

The exec summary's "X / Y Reviewers Signed Off" and Reviewer Completion % now count each reviewer once ("signed" = ALL their certs signed — same definition as Get-SPDistinctReviewerSignOff); reassigned entries arrive one-per-cert and previously inflated both figures. Group-SPReviewerActions aggregation fixed alongside: Phase is SIGNED only when every cert is signed (was first-enumerated-cert-wins) and SignOffDate is the most recent (was first-non-blank-kept-forever).

9d. E4 — V4e coverage counts the independent undecided fact — f73f208

"Series attestation coverage" now subtracts items whose independent IsPersistentlyUndecided flag is set (never genuinely decided anywhere in the series) instead of the masked Classification — brand-new undecided entitlements no longer count as "genuinely attested" (10 new undecided items could previously render "100% genuinely attested").

9e. C3 — leadership level-report drill-down/nav links — 444be5f

Subordinate drill-down and parent nav links now mirror the actual filename scheme (prefix-name-id-runStamp.html): Export-SPLeadershipLevelHtml takes a -RunStamp shared across every level of a report set (threaded by the band-filtered wrapper), links embed the target's id + stamp, and the dead executive-summary.html fallback link was removed. Every up/down link in the generated set now resolves. VERIFIED: 252/252 report/leadership/reviewer/V4e tests pass
