Getting Started

This section walks you from a fresh toolkit extract to your first audit report in under 15 minutes. It covers prerequisites, configuration, connectivity testing, and safety defaults.

What This Toolkit Does

The SailPoint ISC Governance Toolkit is a PowerShell 5.1 toolkit for automated testing and auditing of SailPoint IdentityNow (ISC) certification campaign workflows. It creates, activates, and validates certification campaigns against the ISC REST API v3, producing structured JSONL evidence and HTML reports for UAT sign-off, compliance audits, and daily governance operations.

The toolkit covers three governance domains:

  • Campaign Audit -- post-campaign compliance reporting with reviewer accountability, decision breakdowns, remediation proof, and leadership rollups
  • Delta Certification -- daily AD access change detection with automatic SEARCH campaign creation per manager group, escalation for stale certifications, and orchestrated daily workflows
  • Disconnected App Onboarding -- flat file CSV integration for applications without native ISC connectors, with delta detection, identity resolution, and batch orchestration

Required PAT Scopes (Read-Only Audit)

The toolkit's audit and reporting features require 6 read-only scopes on your ISC Personal Access Token:

Scope Purpose
idn:campaign:read Query campaigns, certifications, and access review items
idn:campaign-report:read Download campaign status and signoff reports
sp:report:read Access ISC report exports (CSV format)
sp:search:read Identity resolution (manager lookup, email correlation)
idn:sources:read Source metadata for coverage analysis
idn:accounts:read Account details for identity-to-account mapping
Important

Delta Certification's GET /v3/account-activities endpoint requires sp:scopes:all or a browser token. The 6 read-only scopes above are not sufficient for Delta Cert operations. Use the -Token parameter with a browser JWT as a workaround.

For the complete API client setup walkthrough (including how to create a PAT in the ISC admin console), see docs/SANDBOX-API-SETUP.md.

Configuration

The toolkit uses a single Config\settings.json file. On first run, Test-SPConnectivity.ps1 auto-generates the file from a template and exits with guidance. Open the file and replace all CHANGE_ME values.

Minimum Required Configuration

Only four values need to change for basic operation. Replace acme with your ISC tenant name:

{
  "Global": {
    "EnvironmentName": "Sandbox"
  },
  "Authentication": {
    "Mode": "ConfigFile",
    "ConfigFile": {
      "TenantUrl": "https://acme.api.identitynow.com",
      "OAuthTokenUrl": "https://acme.api.identitynow.com/oauth/token",
      "ClientId": "your-client-id-here",
      "ClientSecret": "your-client-secret-here"
    }
  },
  "Api": {
    "BaseUrl": "https://acme.api.identitynow.com/v3"
  }
}
Note

All three URLs use the api. prefix: https://<tenant>.api.identitynow.com. This is the correct format for both the tenant URL and the OAuth token URL.

First Run: Test Connectivity

After configuring settings.json, run the connectivity test to verify your configuration, credentials, and network access:

.\Scripts\Test-SPConnectivity.ps1

Expected output -- three steps, all PASS:

  [PASS] Step 1: Load and validate settings.json (12ms)
         Environment: Sandbox | Mode: ConfigFile
  [PASS] Step 2: Acquire OAuth 2.0 bearer token (340ms)
         Mode: ConfigFile | Expires: 2026-02-18T15:12:49Z
  [PASS] Step 3: GET /v3/campaigns?limit=1 (180ms)
         API responded successfully. Items returned: 1

  RESULT: All connectivity checks passed.
What Each Step Validates

Step 1 loads and validates Config\settings.json (required keys, URL formats). Step 2 acquires an OAuth 2.0 bearer token using the configured credentials. Step 3 makes a live API call (GET /v3/campaigns?limit=1) to confirm network access and that the token has sufficient permissions.

Your First Audit

Once connectivity is confirmed, run your first campaign audit. Start with a dry-run to see what campaigns match your filter without generating reports:

# Dry-run: see matching campaigns without generating reports
.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -DaysBack 7 -WhatIf

Then run the actual audit:

# Audit all campaigns completed in the last 7 days
.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -DaysBack 7

The audit produces per-campaign HTML reports with an Executive Summary Dashboard, decision breakdowns, reviewer accountability, and remediation proof. Output goes to the Audit\ directory by default:

Audit\
    <CampaignName>\
        <CampaignName>_audit.html      # Per-campaign HTML report
        <CampaignName>_summary.txt     # Per-campaign text summary
    CampaignAudit_<CorrelationID>.html  # Combined HTML report (all campaigns)
    CampaignAudit_<CorrelationID>.jsonl # JSONL audit trail
Tip

At least one campaign filter is required. Use -Status, -CampaignName, -CampaignNameStartsWith, or -CampaignNameContains. Without a filter, the script exits with code 2.

Other ways to filter campaigns:

# Audit a specific campaign by exact name
.\Scripts\Invoke-SPCampaignAudit.ps1 -CampaignName 'Q1 2026 Access Review'

# Audit campaigns whose name contains a keyword (substring match)
.\Scripts\Invoke-SPCampaignAudit.ps1 -CampaignNameContains 'entitlement' -DaysBack 90

# Use a browser token instead of configured OAuth credentials
.\Scripts\Invoke-SPCampaignAudit.ps1 -Token 'eyJhbGciOiJSUzI1NiIs...' -Status COMPLETED -DaysBack 7

Safety Defaults

The toolkit ships with conservative safety defaults to prevent accidental changes in production environments. These are configured in the Safety section of settings.json:

Setting Default What It Does
MaxCampaignsPerRun 10 Caps the number of campaigns created per execution. If the toolkit calculates that more campaigns would be needed (e.g., more manager groups than the limit), it aborts before creating any campaigns.
RequireWhatIfOnProd true When set, the toolkit requires operator confirmation via ShouldProcess before proceeding without -WhatIf. This prevents accidental live runs.
AllowCompleteCampaign false Blocks the irreversible POST /campaigns/{id}/complete API call. This endpoint only works on past-due campaigns and its effects cannot be undone.

Additionally, every CLI script supports the -WhatIf parameter for dry-run mode. When -WhatIf is active, the toolkit performs all validation and planning steps but makes no write API calls and creates no campaigns.

Recommendation

Always run with -WhatIf first in a new environment. Review the planned actions, then re-run without -WhatIf to execute. Once comfortable with the toolkit behavior, adjust the safety settings in Config\settings.json as needed.

Authentication Modes

The toolkit supports three ways to authenticate with ISC:

Mode How It Works When to Use
ConfigFile Reads ClientId and ClientSecret directly from settings.json in plaintext Isolated development environments only
Vault Credentials stored in an AES-256-CBC encrypted vault file (Data\sp-vault.enc). Passphrase prompted at runtime. Shared, CI/CD, or production-adjacent environments

Leadership Rollup Reports

Leadership rollups aggregate campaign decisions up the organizational hierarchy, producing per-level reports for VPs, directors, and managers. Enable with -IncludeLeadershipRollup or set Audit.IncludeLeadershipRollup = true in settings.json.

How It Works

  1. The toolkit collects all unique identity IDs from campaign decisions
  2. Build-SPOrgTree walks each identity's ISC manager chain upward to -LeadershipDepth levels
  3. Decisions are grouped by org level using Group-SPAuditByLeadership
  4. Per-level HTML reports are generated for each leader at each level

Org Level Labels

The toolkit assigns labels based on the absolute distance from individual contributors (level 0):

Level Label Typical Role
0 Individual Contributors End users whose access was reviewed
1 Managers Direct managers who reviewed certifications
2 Directors Second-level leaders overseeing managers
3 Vice Presidents Third-level leaders overseeing directors
4 Senior Vice Presidents Fourth-level leaders
5 Executive Leadership C-suite or equivalent

Depth Control

The -LeadershipDepth parameter controls how far up the org tree to walk. The -LeadershipStartLevel parameter controls where report generation begins (-1 = auto-detect, starting from the highest level found).

# Walk 3 levels: identity -> manager -> director -> VP
.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -DaysBack 30 -IncludeLeadershipRollup

# Walk only 2 levels: identity -> manager -> director (no VP reports)
.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -IncludeLeadershipRollup -LeadershipDepth 2

# Walk 4 levels for a large org
.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -IncludeLeadershipRollup -LeadershipDepth 4

Executive Summary Report

The executive summary (leadership/executive-summary.html) provides a high-level view across all directors. It includes overall approval/revocation rates, an SVG donut chart, and a per-director summary table sorted by completion percentage ascending (worst-performing first). Completion cells are color-coded: green for >= 95%, orange for 80-95%, red for < 80%.

Per-Leader Reports

Each leader at each level gets an individual report with:

  • Level-appropriate header (e.g., "VP Report: Alice Johnson")
  • Summary cards showing total items, approved, revoked, and pending counts
  • Subordinate table listing each direct report's decision statistics
  • Navigation links up to parent report and down to child reports
  • At the lowest generated level: full identity decision detail

Detail Levels

The -DetailLevel parameter controls how much identity-level information appears in the HTML reports. All three levels include the executive dashboard, reviewer accountability, and campaign metadata. The difference is in the decision detail tables.

Summary -- Counts and percentages only

Shows aggregate statistics: total items, approval rate, revocation rate, completion percentage, and reviewer count. No per-identity or per-entitlement detail. Best for executive-level distribution where readers need the headline numbers only.

.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -DetailLevel Summary
Detailed -- Identity names and decisions

Includes per-identity rows with name, account identifier, access name, decision, and reviewer. Omits lifecycle events, remediation timestamps, and justification text. Good for manager-level review where the focus is on who-decided-what.

.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -DetailLevel Detailed
Verbose -- Full compliance evidence (default)

Everything in Detailed plus: justification comments, remediation status and dates, identity lifecycle events, risk flags, and the full reassignment chain. This is the default and the level required for SOX/SOC2 compliance evidence packages.

.\Scripts\Invoke-SPCampaignAudit.ps1 -Status COMPLETED -DetailLevel Verbose

IdentityId ISC identity ID

Anti-Rubber-Stamping Detection

The Measure-SPAuditRubberStampRisk function performs four SOX/SOC2 red-flag checks on reviewer behavior, producing a per-reviewer risk severity (None, Low, Medium, High):

Check What It Detects Threshold
Approval-only rate Reviewer approved 100% of items without a single revocation 100% approval across > 10 items
Decision velocity Decisions made faster than humanly possible for the item count > 50 items decided in < 60 seconds
Bulk decision clusters Consecutive identical decisions within a narrow time window > 5 identical decisions within 30 seconds
Response latency First decision made suspiciously soon after campaign assignment < 1 minute after assignment with > 5 items

Severity is calculated as: High = 2+ flags; Medium = 1 flag (velocity or approval-only); Low = 1 flag (other type); None = 0 flags.

Risk Indicators

The Get-SPAuditRiskFlags function adds risk flags to individual access review decisions. Each decision item can receive zero or more of the following flags:

Flag Color Trigger
STALE Orange Last login > StaleAccessDays ago (default 90)
PRIVILEGED Red Entitlement name matches PrivilegedPatterns (Admin, Root, DBA, Domain Admins)
ORPHAN Red Identity has no manager assigned in ISC
TERMINATED Red Identity lifecycle state is terminated
SVC-ACCOUNT Gray Identity name matches ServiceAccountPatterns (^SVC-, ^svc-)

Risk indicator thresholds are configurable in settings.json under Audit.RiskIndicators:

"Audit": {
    "RiskIndicators": {
        "StaleAccessDays": 90,
        "PrivilegedPatterns": ["Admin", "Root", "DBA", "Domain Admins"],
        "ServiceAccountPatterns": ["^SVC-", "^svc-"]
    }
}

Delta Cert Overview

The delta certification workflow addresses a gap in ISC's native certification capabilities: there is no built-in way to automatically certify only new access grants on a daily basis. Standard ISC campaigns review all entitlements for a population, which is too broad for day-to-day change detection. The toolkit fills this gap with an event-driven approach.

How It Works

  1. Event Detection -- Get-SPDeltaGrantEvents queries GET /v3/account-activities for GRANT_ACCESS events on specified AD source IDs within a configurable time window (default: 24 hours).
  2. Identity Resolution -- Get-SPDeltaAffectedIdentities resolves each event to an active ISC identity, filtering out terminated, inactive, leaver, and prehire lifecycle states. Additional exclusion filters (display name patterns, explicit identity IDs) are configurable.
  3. Manager Grouping -- Group-SPDeltaByManager groups affected identities by their ISC manager, forming one reviewer group per manager.
  4. Campaign Creation -- Invoke-SPDeltaCertRun creates one SEARCH-type certification campaign per manager group, scoped via identity ID filter (id:"abc" OR id:"def"). Each campaign is started immediately after creation.

Campaign naming convention: {Prefix} {YYYY-MM-DD} - {ManagerName}

Scope Requirement

Important: GET /v3/account-activities requires sp:scopes:all -- there is no granular scope for this endpoint. Use a browser token (-Token) from the ISC admin console as a workaround, or configure a PAT with sp:scopes:all.

Output Structure

DeltaCert\

Reviewer Modes

The -ReviewerMode parameter (or DeltaCert.DefaultReviewerMode in settings.json) controls how certification campaigns are routed to reviewers.

Mode Campaign Type Grouping Best For
Manager (default) SEARCH One campaign per manager group. Each manager reviews only their direct reports who received new AD access. Organizations where managers are accountable for their team's access.
SourceOwner SOURCE_OWNER One campaign per AD source ID. ISC automatically routes certification items to whoever owns each source. Organizations where application/source owners control access decisions. Fewer API calls (skips identity resolution and manager grouping).

Manager Mode Flow

Get-SPDeltaGrantEvents (GRANT_ACCESS events)
  -> Get-SPDeltaAffectedIdentities (resolve to active identities)
    -> Group-SPDeltaByManager (one group per manager)
      -> For each manager:
           New-SPCampaign -Type SEARCH -SearchFilter 'id:"x" OR id:"y"' -CertifierIdentityId $managerId
           Start-SPCampaign

SourceOwner Mode Flow

Get-SPDeltaGrantEvents (GRANT_ACCESS events)
  -> For each unique SourceId:
       New-SPCampaign -Type SOURCE_OWNER -SourceId $sourceId
       Start-SPCampaign

Campaign Cleanup

Over time, managers may neglect to act on their delta cert campaigns, causing campaign pile-up. Invoke-SPDeltaCertCleanup finds past-due delta cert campaigns and completes them, preventing stale campaigns from accumulating.

How Cleanup Works

  1. Searches for active campaigns matching the campaign name prefix via Search-SPCampaigns -Keyword $Prefix -Status @('ACTIVE')
  2. For each campaign, checks if the deadline has passed or if the campaign is older than CleanupDaysStale (default: 3 days)
  3. Calls Complete-SPCampaign -CampaignId $id on past-due campaigns
  4. Returns a summary: campaigns completed, campaigns still active, errors
Safety Guard: Complete-SPCampaign is guarded by Safety.AllowCompleteCampaign (default: false). You must set this to true in settings.json for cleanup to work. When blocked, the function returns Success=$false with a clear error message and makes no API calls.

Triggering Cleanup

Cleanup runs when you pass -RunCleanup to Invoke-SPADDeltaCert.ps1. It executes before creating new campaigns. Example:

# Run cleanup then create new campaigns
.\Scripts\Invoke-SPADDeltaCert.ps1 -SourceId 'src-abc123' -RunCleanup -Token $token

Configuration

Setting Default Description
DeltaCert.CleanupDaysStale 3 Days before an active delta cert campaign is considered stale and eligible for completion.
Safety.AllowCompleteCampaign false Must be true for cleanup to call the ISC campaign-complete API.

Escalation

When a reviewer does not act on a certification within a configurable threshold, the toolkit can escalate by reassigning the certification to the reviewer's manager in the ISC org tree.

Escalation Workflow

  1. Stale Detection -- Get-SPDeltaCertStaleCertifications finds active delta cert certifications where signed is null (not completed) and created is older than StaleHours (default: 24).
  2. Org Tree Walk -- Invoke-SPDeltaCertEscalate looks up each stale reviewer's manager via Get-SPDeltaIdentityDetail.
  3. Reassignment -- Calls Invoke-SPReassign to reassign the certification to the reviewer's manager. The reassignment reason includes the hours-open context: "SLA escalation: 48 hours without action".
  4. ISC Notification -- ISC sends its own email notification to the new reviewer when a certification is reassigned. No custom email logic is needed.

Escalation Safeguards

Safeguard Behavior
No manager Reviewer with no manager in ISC is skipped with a WARN log (not an error).
Max escalation levels MaxEscalationLevels (default: 2) prevents infinite escalation loops. If the reviewer's manager was already the target from a previous escalation, the walk goes up one more level.
Large certifications Certifications with >50 review items automatically use Invoke-SPReassignAsync (max 500 items) instead of the synchronous endpoint (max 50).
Governance Groups Reassignment does NOT work for Governance Group certifications (documented ISC exception). These are detected and skipped with a WARN log.

Disconnected App Overview

Many enterprise applications -- legacy mainframe systems, vendor-hosted SaaS platforms, niche financial tools -- have no SailPoint ISC connector and no public API. The only viable integration path is flat-file import: the app team extracts a CSV of current accounts and entitlements, places it on a shared drive or SFTP location, and the toolkit picks it up for governance.

Why Flat Files?

  • No connector available -- ISC has ~200 connectors, but thousands of enterprise apps fall outside that catalog (e.g., PEP+ by Fiserv, DebtNext dPlat, IPAY by Jack Henry).
  • No admin API -- even SaaS apps may not expose a REST API for reading account/entitlement data.
  • Compliance deadline -- building a custom connector takes weeks to months; flat-file onboarding can begin the same day.
  • Phase 1 / Phase 2 pattern -- start with flat-file CSV governance (Phase 1), then invest in a custom connector only if the app's user volume and churn rate justify it (Phase 2).

Single App Processing

Invoke-SPDisconnectedAppCert.ps1 runs the full daily certification pipeline for a single app: validate, snapshot, detect deltas, resolve identities, create campaigns, and generate reports.

Pipeline Steps

  1. Validate -- Test-SPDisconnectedAppAccountFile checks CSV structure and data integrity. If an entitlement file is provided, Test-SPDisconnectedAppEntitlementFile and Test-SPDisconnectedAppCrossReference also run.
  2. Snapshot -- Save-SPDisconnectedAppSnapshot copies the current CSV to {SnapshotDir}/{AppName}/{YYYY-MM-DD}-accounts.csv. Idempotent: re-running on the same day does not create duplicate snapshots.
  3. Previous Snapshot -- Get-SPDisconnectedAppPreviousSnapshot finds the most recent snapshot before today. Returns $null on first run.
  4. Delta Detection -- Compare-SPDisconnectedAppFiles compares today's file against yesterday's snapshot. Seven change types detected (see Delta Detection below).
  5. Threshold Check -- Test-SPDisconnectedAppDeletionThreshold blocks processing if account removals exceed AccountDeletionThresholdPct (default: 20%). Prevents mass-revocation from corrupt or truncated CSV files.
  6. Identity Resolution -- Resolve-SPDisconnectedAppIdentities resolves changed accounts to ISC identities via POST /v3/search (email primary, username fallback). Session-level cache avoids duplicate API calls.
  7. Campaign Creation -- Invoke-SPDisconnectedAppCertRun groups resolved identities by manager and creates one SEARCH campaign per manager. Includes duplicate campaign detection and MaxCampaignsPerRun safety guard (default: 20).
  8. HTML Report -- Export-SPDisconnectedAppDeltaHtml generates a self-contained delta report with six sections.
  9. Audit Event -- JSONL audit trail entry appended for compliance evidence.

Delta Detection

Compare-SPDisconnectedAppFiles compares today's account CSV against yesterday's snapshot and classifies every account into one of seven change types. The comparison uses O(1) hashtable lookups keyed by the id column for performance.

Change Types

Change Type Detection Logic Triggers Campaign?
AccountAdded Account ID exists in today's file but not in yesterday's snapshot. Yes
AccountRemoved Account ID exists in yesterday's snapshot but not in today's file. No (informational)
AccountDisabled IIQDisabled changed from false to true. No (informational)
AccountEnabled IIQDisabled changed from true to false. Yes
EntitlementGranted New entitlement ID(s) appear in the groups column compared to yesterday. Yes
EntitlementRevoked Entitlement ID(s) removed from the groups column compared to yesterday. No (informational)
AttributeChanged Any other column value differs between today and yesterday (e.g., name, email, department). No (informational)

Only three change types trigger certification campaigns: AccountAdded, AccountEnabled, and EntitlementGranted. These represent new or expanded access that requires manager review. Removals, disables, and attribute changes are captured in the delta report for audit visibility but do not create campaigns.

First Run Behavior

On the first run for an app (no previous snapshot exists), all accounts in the CSV are treated as AccountAdded. This creates campaigns for every identity in the file, establishing the baseline. Subsequent runs detect only day-over-day changes.

Deletion Threshold Protection

Test-SPDisconnectedAppDeletionThreshold prevents mass-revocation from corrupt or truncated CSV files. If the percentage of removed accounts exceeds AccountDeletionThresholdPct (default: 20%), processing is blocked.

Scenario Behavior
First run (no previous snapshot) Threshold check bypassed -- all accounts are Added.
Previous snapshot has < 5 accounts Threshold check bypassed -- too few accounts for meaningful percentage.
Removals <= 20% of previous count Processing continues normally.
Removals > 20% of previous count Processing blocked. Exit code 5. Investigate the CSV before re-running.
Threshold exceeded? Verify that the CSV file is complete and not truncated. If the removals are legitimate (e.g., a department was offboarded), increase DisconnectedApps.AccountDeletionThresholdPct temporarily, re-run, then restore the default.

Remediation Tracking

When a reviewer revokes an entitlement in an ISC certification campaign, that decision must be verified against the next day's CSV to confirm the app team actually removed the access. The remediation tracking workflow bridges this gap between ISC governance decisions and real-world access removal.

How It Works

  1. Decision harvest -- Get-SPDisconnectedAppCampaignDecisions queries completed campaigns and collects revocation decisions (see Decision Collection below).
  2. Record creation -- New-SPRemediationRecord writes revocation details to remediation-tracker.json in the app's report directory. Each record includes: identity, entitlement, campaign ID, decision timestamp, and status (Pending).
  3. Verification -- On the next daily run, delta detection identifies EntitlementRevoked changes. The toolkit cross-references these against pending remediation records to confirm removal.
  4. Status update -- Confirmed removals are marked Remediated with the verification date. Unconfirmed removals remain Pending and are flagged in the team dashboard and batch summary.

Remediation States

State Description
Pending Revocation decision made in ISC but not yet confirmed in next-day CSV.
Remediated Entitlement removal confirmed: the group no longer appears in the account's groups column.
Overdue More than DeadlineDays elapsed since the revocation decision with no confirmation.
No provisioning API: Disconnected apps by definition lack an API for automated access removal. The revocation decision in ISC is a directive to the app team, not an automated action. Remediation tracking provides accountability evidence that the directive was fulfilled.
